# Logging for 2026-10-15

## 02:40 UT (continuing the sweep)

Full Kast sweep finished: **308 runs** (11 tables x 14 dates x with/without a
manual start and a mid-night block). 264 scheduled something, 44 empty, **no
crashes and no invalid schedules**. The 44 empties are the wrong-season and
wrong-hemisphere combinations, each target carrying a reason.

Confirmed Keck is structurally immune to the DST bug: Pacific/Honolulu has a
single UTC offset all year, so wall-clock and elapsed-time arithmetic never
diverge there. The bug could only ever have hit Lick.

Probed inputs the sweep does not generate, and found two more:

**Bug 3: a duplicated target name is observed twice.** A table with three
targets repeated came out as six scheduled blocks, 190 minutes spent
re-observing the same objects. The scheduler has no way to notice. This is
not hypothetical -- merging two sources is exactly how the baseband targets
reached Lick-2026B-03. `load_targets()` now refuses, naming the repeats.
Checked the guard against all 15 real target tables in Night_plans/ first:
none has duplicates, so nothing that works today starts failing.

**Bug 4: `--start` after dawn gives a negative-length night.** `--start 07:00`
on an October night printed "0 min science / -73 min night (-0%)" and
scheduled nothing, which reads like "no targets are up" rather than "your
start time is a typo". Now refused with the twilight time in the message.

54 tests pass. The LRIS sweep is still running -- the Keck path samples
observability every 10 minutes with a scalar astropy call per sample, so a
single 9-target run takes 19 s and the 40-target table proportionally longer.

## 03:30 UT

LRIS sweep (44 runs, 4 dates) came back **35 ok, 8 empty, 1 INVALID**:
`SIMTDE23430: ends 21:17, after its window closes 21:12`.

Not a bug, but worth the look it got. The Keck scheduler deliberately fits a
block against `window_end + timedelta(minutes=10)` -- a bare magic number
sitting under a comment about something else. The justification turns out to
be sound: `find_observable_window()` samples the night every 10 minutes, so
the true edge of the airmass window lies somewhere inside the step past the
last good sample, and one step of grace is the honest width of that
uncertainty. It is not spare observing time, and widening it would schedule
above the airmass limit.

Named it `WINDOW_SAMPLE_MIN`, used it for both the sampling and the grace so
the two can no longer drift apart, and taught the sweep's checker that Keck
has this slack while Lick -- whose windows are analytic hour-angle limits --
has none. Re-running the LRIS sweep with the DST dates and the manual-start
variants added.

Four real bugs from the exercise, then: the empty-night crash, the DST
arithmetic, duplicate target names scheduled twice, and a start time after
dawn producing a negative-length night. Plus one piece of undocumented
behaviour that now explains itself.
