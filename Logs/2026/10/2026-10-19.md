### Narrative

Follow-on from the AstroScheduler comparison: install/run steps for a teammate
pulling that repo fresh. Rather than transcribe its README I built a clean venv
in the scratchpad and ran the steps, which was the right call — two things in
the README are wrong and one of them is a genuine bug.

The port is **8055**, not 8000: `app.py` reads `os.environ.get("PORT", 8055)`.
Minor. The real finding is that `pip install -r requirements.txt` alone
**silently disables astropy**. `requirements.txt` pins `astropy>=5.3`, so pip
resolves astropy 8.x, where `get_moon` no longer exists; `scheduler.py` wraps
the import in `try/except ImportError` and sets `HAS_ASTRO_LIBS = False`. No
error, no warning — the app starts and schedules, but five code paths quietly
swap astropy for internal approximations, so moon separation and twilight get
less accurate and nobody is told. Verified the matrix: astropy 8 + numpy 2 =
silent fallback; astropy 6 + numpy 2 = hard crash (`np.in1d` removed in numpy
2, and an `AttributeError` is not caught by that `except ImportError`); astropy
6 + numpy 1.26 = works. So the fix is `pip install "astropy<7" "numpy<2"`.
Confirmed the server serves (HTTP 200) and the 31 unit tests pass in ~50 s.
Offered to draft a patch for UCSC-Transients but left their repo untouched.

**Tokens/CO2:** see `Logs/log_summary.csv` for authoritative values.

### Narrative

Implemented per-target priority end to end, planned first (plan approved, saved
at `~/.claude/plans/magical-puzzling-river.md`). Three decisions were put to the
author and all three recommendations were taken: priority is a float with lower
= better and default 1; the priorities page becomes the final step and owns the
Generate button; Lick/Kast first with Keck/LRIS deferred.

The recheck changed the design I had sketched in
`docs/priority_comparison_astroscheduler.md`. I had assumed we could copy
AstroScheduler's "already-placed targets become mandatory" trick by passing
tier-1 placements to a second `schedule_greedy` pass as blocks. That does not
work here: `fit_around_blocks` can only ever push a target *later*
(`candidate_start` is monotonically non-decreasing), and `schedule_greedy` walks
a cursor that never rewinds — so one more pass over the whole night would sail
past every gap it had already crossed. The repo had already solved this at
`lick_2026b02_night2_calculations.py:366-386`: compute the gaps, then call
`schedule_greedy` once per gap, restarting the cursor inside each. Mirrored that
instead of inventing a solver. Worth recording as a general lesson — the
comparison doc's recommendation was right about *what* to build and wrong about
*how*, and only reading the primitives caught it.

Second thing the recheck turned up: `--max-targets` took
`nsmallest(n, 'start_pst')`, i.e. trimmed by time. Left alone it would have
thrown away a top-priority late target to keep a filler that started early,
silently undoing the tier loop. Now sorts by `(priority, start_pst)`.

Built it in four parts. `targets_io` gained `priority` in `ALIASES`/
`OPTIONAL_FIELDS`, a `DEFAULT_PRIORITY = 1.0`, and numeric coercion handled
*apart* from the other optional fields because it is the one the scheduler
computes with. Unreadable values (the `A`/`B` that
`make_test_target_tables.py` emits) fall back to the default rather than
raising — but a new `priority_coercions()` makes that reportable, since
silently dropping the column is the exact behaviour this field exists to fix.
`analyze_targets` carries the column, from where it propagates for free through
`dict(row, ...)` into every schedule frame. `TargetDecision` gained a
*defaulted* `priority` so existing `plan_result.json` files still load, and the
kast adapter now prefixes reasons with the tier via `_with_priority` — which
deliberately prints nothing when everything is in the default tier, rather than
stamping P1 on every row.

The governing constraint throughout was that an un-prioritised table must
schedule exactly as before. `schedule_by_priority` short-circuits to the single
`schedule_greedy` call when there is one tier, and `test_priority_tiers.py`
asserts the two produce identical schedules. That test is the real deliverable.

Frontend: the Inspect button stopped being an in-place check and became the
page's single forward action, moved to the bottom of the setup card. The hard
constraint is that `frontend/app.js` has **no persistence of any kind** and
`useTemplate()` clones a fresh template on every route change, so the whole
setup form now gets stashed in `state` before navigating. A browser reload on
`#/priorities` still loses it, and since nothing is on disk yet there is no
`dir=` to re-fetch from — so that case renders an honest notice back to setup
rather than an empty page. Priorities travel to the scheduler as a column in a
derived `targets_with_priority.csv` written into the plan directory, not as a
request field, which is what makes a GUI plan reproducible: verified by running
the CLI on that file and getting a byte-identical schedule.

Caught a pre-existing bug while moving code: `stopPolling()` was called in the
generate handler's `finally` but is a `const` local to the finders page — a
ReferenceError that left the Generate button stuck disabled after any failed
generate. Fixed it in the handler I moved. The identical bug still sits in
`renderStarlist` (line ~1084); flagged rather than fixed, as it is unrelated to
priorities.

End-to-end check through the running server: a target the greedy pass bumped
(`SIMFRB16012`, "needs 90 min but only 41 min left in its HA window") is
scheduled first at 20:11-21:41 once promoted above the rest. 68 tests pass, up
from 54. Smoke-test plan directories removed afterwards.

### Narrative

Measured before building. The author's own `Lick-2026A-07_host_wg` plan had
**211 minutes idle** across three gaps (15, 52, 144 min) with two rejected
targets — a good concrete case to design against rather than guessing.

Added `backfill_partials()` to `kast_calculations.py`, running after the tier
loop: anything dropped for want of time is placed anyway into a leftover gap,
truncated to whatever the overlap of that gap with its own HA window allows.
The constraint that mattered most was the one the author did *not* say: a
partial must never move something already scheduled, and must never point the
mount outside the target's HA window just because the exposure is short. Both
have their own tests.

Labelled via the existing `notes`-prefix convention that `FORCED` already uses,
so the viewer needed almost nothing: `PARTIAL` gives a new `--partial` colour
(pink, deliberately unlike the amber `--forced`, because forced is something
the observer asked for and partial is the planner's own doing), a legend entry,
and a pill in the plan table. The note says exactly what was lost — *"23 of the
90 min this target needs (25%) ... expect low S/N, and drop it if you would
rather have the gap"* — which is the whole contract: truncation is only
acceptable because it is visible and reversible. Added a "Leave idle time idle"
checkbox and a `--no-partials` / `--min-partial` pair of flags.

Two honest findings worth more than the feature.

**First: on the author's actual plan this changes nothing.** Both rejected
targets there have HA windows that do not overlap any idle gap — FRB20260619A's
window (19:49-20:05, 16 min) closes *before* science even starts, because focus
plus the evening standard eats the first 20 minutes. So its 211 idle minutes
are an exhausted-pool problem, not an all-or-nothing-rejection problem. Every
one of the nine targets is either scheduled or window-closed by the time the
144-minute gap opens. Truncation cannot help; only more targets, or deeper
integrations on ones already scheduled, would. Said so rather than quietly
shipping a feature that appears to miss its stated goal.

**Second: it works well where the pool is genuinely oversubscribed.** On
`autumn_ffffpz` the same night went 8 targets / 510 min science (85%) to
9 targets / 533 min (88%), idle down to 24 min.

Two bugs of my own, both caught by running rather than by reading. Rebuilding
the frame from a list mixing pandas Series and dicts made pandas try to align
them and die on `'dict' object has no attribute 'dtype'`; fixed by going
through `to_dict('records')` throughout. Then the full suite caught a real
regression — on a night where nothing is up, `schedule_greedy` returns a frame
with no columns at all, and asking it for `'scheduled'` raised `KeyError`. The
existing schema-guarantee comment in `run()` warns about exactly that case and
I had inserted my pass *above* it. Guarded.

One cosmetic thing noticed and left alone: the kast adapter passes no
`overheads=`, so the focus/standard block at the head of the night shows as
idle rather than overhead. Pre-existing, unrelated, and it makes `idle_min`
read ~15 min high on every Lick plan.

## 22:34 UT

**Prompt:** make a tutorial file in docs for how to make a good target csv file

**Model:** Opus 5. **Tokens/CO2:** see `Logs/log_summary.csv` for the
authoritative figures.

Wrote [`docs/target_csv_guide.md`](../../../docs/target_csv_guide.md), and a
script to go with it.

The framing I settled on is the distinction between a file that *loads* and a
file that makes a *good night*. Those are two different documents in most
projects and it would have been easy to write only the first — a column
reference table, a list of accepted spellings, done. But the column reference
is the part a reader can recover from the error messages anyway; `targets_io`
already names every alias it looked for when it refuses. What is not
recoverable from the error messages is that magnitude sets exposure, that
magnitude 19.2 versus 19.4 is half an hour of telescope time, that a list of
thirty priority tiers is a hand-written running order rather than a priority
scheme, and that you want to oversubscribe by 1.5-2x. So the guide is in two
halves, with the mechanical half kept short.

Everything in it was checked against the code rather than remembered: the
alias lists and the unit-inference ladder from `targets_io.detect_mapping`,
the four refusal paths from `load_targets`, the magnitude-to-exposure bands
from `estimate_kast_exposures.estimate_exposure`, the Dec and HA limits from
the per-run scripts, and the seasonal RA table from the existing docs index.

The script is `scripts/check_target_csv.py`. The gap it fills is real: the
only way to find out whether a table was readable was to start the server and
press Inspect, or to run a whole night's calculation and read the rejections.
`check_test_tables.py` exists but is a smoke test over `test_targs/`, not a
validator for a file someone just wrote. The new one takes a path, prints the
detected mapping with the inferred RA unit, reports priority coercions,
and then — the part that makes it more than a parser — prints best-possible
airmass, the exposure each magnitude implies, and the total science hours, so
a reader can see *before* planning that their list is 40 hours long or that a
third of it sits above the Dec limit. Exits 1 when unreadable, 0 when merely
poor, on the grounds that whether a list is worth the night is the observer's
call.

Two things I got wrong and fixed by running it. `SITES` in `adapters.py` is a
dict of dicts keyed by *instrument*, not an object keyed by site, so
`SITES['lick'].location` was wrong twice over; the flag is now `--instrument`
with `kast`/`lris`. And I had the Shane's Dec +82 limit as a module constant
applied regardless of instrument — Keck has no equivalent hard ceiling, so
borrowing the number there would have been a confident lie. It is now a dict
keyed by instrument and the check is skipped where there is no limit. Added a
caveat line for the same reason on the exposure totals, which are the Kast
dual-beam heuristic and only indicative elsewhere.

The worked example at the end of the guide is run output, not invention: I
wrote both CSVs to the scratchpad and ran the checker on them. That caught a
small inaccuracy in my own prose — I had claimed the bad table reports both
the duplicate name *and* the thrown-away `high`/`low` ranking, when in fact
the duplicate refusal short-circuits before the priority report. The mapping
line above the refusal does show `priority <- Rank`, so the guide now says
that, and that the coercion warning appears on the next run.

Indexed in `docs/README.md` under general documentation, in the scripts table,
and in Getting Help. 78 tests still pass.
