The header carries `TUB = 194.80`, and -- this is the part that matters --
also `HA = -2:23:23.43` and `DEC = 78:14:43.2`. That makes the frame a
calibration of the question left open on 2026-10-14, when an observer's
report of 195.2 on FRB20260418B suggested the Shane tub might read ~24.4 deg
off sky north. I deliberately did not bake that in. **It was wrong.**

Inverting calcint.c: TUB 194.80 -> sky PA 223.85, slit axis **43.85 deg**.
The parallactic angle at that instant, from the header's own HA and Dec, is
**42.54 deg**. Agreement to **1.31 deg** -- about the precision of setting a
tub by hand. calcint.c's zero point is right, and the slit was set to
parallactic. Recorded that in `night_planner/lick_tub.py` with the frame
cited, so the question cannot be reopened from the anecdote alone.

Checking the other twelve frames of that target makes the picture sharper.
The tub was set once per block and left: 193.2/194.8 for the first block at
HA ~ -2.3h, nudged to 195.2 for the second at HA ~ -1h. At the start of the
first block the tub matched parallactic to 0.9-1.3 deg. By the last frame,
HA -0:28, parallactic had rotated to 8.6 deg while the tub still implied
44.3 -- **35.7 deg off**. At Dec +78 near transit the parallactic angle moves
very fast, and the observer did not chase it.

That is our own "off parallactic" number, measured on real data rather than
modelled, and it is the strongest argument yet for the exposure-length
analysis from 2026-10-13: past about 90 minutes on a target like this one, a
single slit setting stops being defensible. Here the second block ran ~50 min
and gave away most of a right angle.

Two scripts, both reusable rather than one-off: `scripts/tub_from_header.py`
inverts TUB to a sky PA and compares it with the parallactic angle implied by
the header, and `scripts/finder_from_frame.py` draws a finder showing how a
frame was *actually* observed -- pointing, slit width, angle and the
parallactic drift across the exposure, all read back out of the header. The
chart is written to
`DATA/REDUCTION/Lick-2025B-3/2025-10-23/finders/FRB20250118B_r2046_observed.png`.

Used the catalogue host position (RA 2.845524 h, Dec +78.246969, mag 17.84,
from the archived Lick-2026B-01 PATH candidates) rather than the telescope
pointing; they differ by 5.9", so the chart centres on the host. 54 tests

## 09:15 UT

**Prompt:** Looking at the finder, we look a bit off, like we didn't acquire the target in the slit, or Is this a plotting issue

**Model:** claude-opus-5. **Tokens/CO2:** see `Logs/log_summary.csv` (authoritative).

Neither, and the author's eye was right. Took the two questions separately.

*Is the drawn slit centred on the plotted position?* Computed the
perpendicular distance from the target to the slit's great circle:
**0.0000"**. The geometry is exact; no plotting bug.

*Is the plotted position on the galaxy?* First attempt used DAOStarFinder,
which found nothing -- it is a *star* finder and filters on roundness, so it
rejects an extended host. Switched to smoothed local maxima above 4 sigma,
which is the right tool for the question. Result:

- the **telescope pointing** from the header is **0.34" from a 13-sigma
  source**
- the **catalogue position I used** is **5.56" from that same source**

So the observers acquired correctly and **my coordinate was wrong**. All
three archived files carrying FRB20250118B give dec 78.2469692 sitting next
to `DM` and `P_Ux` -- that is the *burst* position, not the host, which is at
78.2453. `targets_io` guards against exactly this by excluding FRB_RA/FRB_Dec
from its aliases; I bypassed the guard by reading the CSV by hand with
pandas and taking a column called `dec`.

With a 2" slit, 5.9" means missing the galaxy entirely. If that chart had
been used at the telescope it would have produced an empty spectrum and a
confusing night.

Redrew on the header pointing -- the circle now sits on real light with the
slit through it -- and added the guard that would have caught me:
`finder_from_frame.py` now warns when a supplied position is further from
the telescope pointing than the slit is wide, naming the burst-vs-host
confusion as the likely cause. Also kept
`scripts/check_target_on_source.py`, which answers "is this coordinate on
anything?" for any position, since that is the question I should have asked
before drawing.

The lesson is not that the catalogue is bad -- it is that a hand-rolled
`pd.read_csv` skips the one piece of code written to prevent this. 54 tests
pass.

The central result is negative and worth stating plainly: **there is no

mag-19/Dec-82 handoff back to Lick), which reject but never rank; (3) the
greedy earliest-window-close-first scheduler, which is pure *urgency* and blind

pools, and author statements in prose.

builds a deliberately lower-priority pool (`AmbiguousHost`/`TooDusty`,

### Narrative

The prompt file had grown a second item since the previous turn — item 1 was
now numbered and item 2 pointed at
`/home/lordrick/Projects/fun_side_projects/ryan_scheduler/AstroScheduler`:
*"Read, explain and compare with the priority in ..."*. Re-read the file first
rather than assuming the version from the previous turn, which was the right
call. AstroScheduler is a separate repo (UCSC-Transients), so I read it and
wrote nothing into it.

The comparison turned out to be unusually fair: AstroScheduler schedules **the
same telescope** (Lick Shane 3 m) and adopts the **same HA limits** we do
(-5.6667 / +3.75). So the physics layer is shared and the only real difference
is the priority model. Two discrepancies fell out of that and are flagged for
the author: their `ShaneTelescope` declares `dec_min=-35.0, dec_max=72.0`
against our `DEC_LIMIT = 82.0` with no southern limit at all — both cannot be
right — and their slew is a flat 7 min against our `SLEW_MINUTES = 5`.

AstroScheduler has what we lack: `Target.priority` is a float, 1 = highest,
with `0.0` reserved as a standard-star sentinel (checked by identity, and it
buys a looser twilight rule). It is authored by hand — `priority = X` in the
target file, default 3.0 in the JS parser and 1.0 in the API — not derived
from any catalog.

The consumer is `_solve_internal()`, a priority-sequential Branch and Bound.
The design move worth copying is the tier loop: targets are partitioned by
priority, tiers solved best-first, and everything already placed re-enters the
next tier's search as **mandatory** (`S_active`) while the new tier's targets
are optional. That yields a guarantee we do not have — a low-priority target
can never displace a high-priority one — but, importantly, it still allows a
high-priority target to be *re-positioned* so a lower one can exist. A
one-pass greedy cannot do that, and it is exactly the FRB20250408A failure
mode recorded in the brain (v0.37/v0.38).

Inside a tier the objective is `median_airmass + 1000.0 * twilight_dist`
summed over placements, with `100000.0` charged per dropped optional target.
I spent a little care on reading that correctly: the penalty is ~5 orders of
magnitude above airmass values, so the objective is **lexicographic in
practice** — maximise count first, then minimise airmass — and priority is not
in the cost function at all, only in the tier loop. Likewise the `1000.0`
twilight weight is a soft constraint implemented as cost. Mechanics: greedy
warm start for an upper bound, suffix-minimum pruning, 1-minute chunks, and a
hard `max_search_iterations = 20000` cap — so the result is good, not provably
optimal, and the doc says so rather than calling it exact.

Three override channels sit above priority there: `manual_start_time`
(pre-reserved before tier 1, i.e. infinite priority), `schedule_before`
precedence via topological sort with graceful cycle handling, and
`previous_start_chunks` tried first so a mid-night re-solve does not churn the
rest of the night. That last one has no night-planner equivalent and is
directly useful to us, since we re-run plans constantly.

Also confirmed the client-side JS fallback (`static/app.js:5362-5668`)
reimplements the identical algorithm — same tiers, same 1000.0 and 100000.0
constants — so the dashboard survives the server being down.

Resisted the temptation to make the comparison one-directional. We have things
they do not: staged rejection provenance with a `limit_reason` per target
(they return a bare `conflicts` list with no reason), an actual catalog behind
the priority, `load_targets()` refusing a burst position in place of a host,
multi-facility handoff, and reproducible per-run scripts. The honest framing,
which became the doc's bottom line: **the two repos are missing opposite
halves of the same system** — they have a consumer with no principled source,
we have a source with no consumer.

Documentation only again; no calculation, so the calculations rule did not
trigger. Wrote `docs/priority_comparison_astroscheduler.md` (223 lines), linked
it from `docs/README.md` and cross-linked it from `priority_system.md`, and
added brain v0.57. Ranked the adoption path cheapest-first in the doc: the
field + alias, then the tier loop wrapping `schedule_greedy` (the cheapest real
fix), then the drop-penalty idiom, re-solve stability, and only last a cost
function of our own.
